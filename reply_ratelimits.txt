Good question — happy to lay it out precisely.

Rate limits. The public MCP endpoint is rate-limited per client IP (it's keyless/no-auth, so the IP is the unit). The ceilings are deliberately generous for agent use — roughly 10 requests/sec for normal tool calls and 5/sec for the heavier search tools, each with short burst headroom on top. If you ever exceeded them you'd get an HTTP 429, not a timeout, and in practice almost no one does — typical agent traffic sits well under. So unless you're firing many parallel calls per second from a single IP, rate limiting is very unlikely to be the cause.

The timeouts are a separate, server-side issue we recently tracked down. Under load, the heavier (LLM-backed) search tools could saturate the worker thread pool, so even light calls occasionally sat in the queue for a long time — made worse by a transient database problem earlier this week. Two things have changed:

- We shipped a 120-second dispatch timeout (matching the gateway's read timeout), so a call now fails fast with a clean, retryable error instead of hanging.
- A full clean rebuild resolved the database problem; latencies are back to normal.

A durable fix — making the LLM calls async and adding caching so heavy tools can't block light ones — is in progress.

On your side, I'd suggest:

- Reuse a single SSE session rather than reconnecting per call.
- Retry on a timeout or 429 with exponential backoff — a retry almost always succeeds now that calls fail fast rather than hang.
- Keep per-IP request rate comfortably under ~5/sec and you'll never see a 429.

If you can share rough timestamps or which tools timed out, I'm glad to dig into those specific calls server-side.

One forward-looking note: if you anticipate directing heavy or sustained traffic to OpenCaseLaw, I'd welcome a conversation about how we might allocate the infrastructure costs. The service is free and public today, but at higher volumes the compute — especially the LLM-backed search — adds up, and I'd much rather work out a sustainable arrangement together than have to tighten the limits for everyone.
