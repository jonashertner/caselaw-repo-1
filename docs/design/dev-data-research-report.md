# Data collection for search / RAG / legal-AI: research report

Scope: what to collect for (a) product-utility measurement, (b) ranking/retrieval improvement, (c) research, (d) model training — mapped onto an MCP+REST legal search API with no UI, ~0.9M tool calls/day.

Purpose mapping: Topic 1 signals serve (a)(b)(d); Topic 2 serves (b)(d); Topic 3 serves (a)(b)(c); Topic 4 serves (c)(d); Topic 5 serves (a) + corpus strategy.

---

## 1. Implicit relevance feedback (clicks without a UI)

**Headline design decision: echo a `result_set_id` in every search response and log the full impression** — ordered candidate ids with rank, per-signal scores, final score, ranker/policy version, session id, raw + parsed query. Any later `get_decision` / `get_erwaegung` / `get_regeste` call for an id that appeared in a prior result set in the same session joins deterministically as the "click", carrying the rank it was shown at. Without the impression log you cannot reconstruct displayed negatives or positions after the fact, and clicks are only interpretable as *relative* preferences within a shown list (Click > Skip-Above), so the unengaged higher-ranked documents are half of every training pair.

Collectible signals:

1. **Impression log** (result_set_id, ordered doc ids + ranks + scores + policy version). Why: the entire counterfactual/unbiased-LTR literature trains on (impression, position, engagement); IPS needs the logging policy and position recorded per event. Sources: Joachims et al., Unbiased LTR with Biased Feedback (WSDM 2017), https://arxiv.org/abs/1608.04468, https://www.cs.cornell.edu/people/tj/publications/joachims_etal_17a.pdf
2. **Fetch-after-search join** (the click analog): follow-up document fetch keyed to (result_set_id, doc_id, rank, time-delta). Derive skip-above pairwise preferences per impression — this is the minimal signal that makes ranking training data useful: query + displayed ids/positions + which were subsequently fetched + session linkage. Everything else is enrichment.
3. **Graded engagement (dwell analog)**: how much of the doc was pulled (number of Erwägungen fetched, repeat fetches), and whether the doc survives into terminal use — appears in `cite()` / `attest_response` / `check_claim_support` or the client's final answer citations (SAT-click analog, the strongest positive). Why: raw clicks are noisy; the classic fix is dwell ≥ 30s = "satisfied click", but the threshold is known not to transfer across page types — for an API, depth-of-retrieval and downstream citation are the better graded measures. Source: Kim et al., Modeling Dwell Time to Predict Click-level Satisfaction (WSDM 2014), https://dl.acm.org/doi/10.1145/2556195.2556220
4. **Session/reformulation chains**: link consecutive queries with a session id; reformulation-then-fetch generates cross-query preference pairs, and reformulation-after-fetch is a dissatisfaction signal. Sources: Radlinski & Joachims, Query Chains (KDD 2005), https://www.cs.cornell.edu/~tj/publications/radlinski_joachims_05a.pdf; Hassan et al., Beyond Clicks: Query Reformulation as a Predictor of Search Satisfaction (CIKM 2013), https://dl.acm.org/doi/pdf/10.1145/2505515.2505682
5. **Position-bias correction hooks**: log ranking policy id per impression; either run occasional randomization (swap interventions), or estimate propensities from logs (regression-EM / DLA), or — newest — use an LLM judge over logged interactions to estimate propensities without interventions (reported +2% weighted NDCG@10 offline when feeding an IPS-weighted reranker). Sources: Ai et al., Dual Learning Algorithm (SIGIR 2018), https://arxiv.org/pdf/1804.05938; Position Bias Estimation for Unbiased LTR in eCommerce Search, https://arxiv.org/pdf/1812.09338; LLMs for estimating positional bias in logged interaction data (2025), https://arxiv.org/pdf/2509.03696. Note: your consumers are mostly LLM agents, which have their own position bias when choosing from result lists — propensity correction still applies; segment logs by client type (agent / dashboard / Word add-in).
6. **Interleaving assignments** (optional online eval): team-draft interleaving logs give ranking comparisons that reach significance with far less traffic than A/B tests. Sources: Chapelle, Joachims, Radlinski, Yue (TOIS 2012), https://dl.acm.org/doi/10.1145/2094072.2094078; Airbnb's combined interleaving + counterfactual evaluation practice (2025), https://arxiv.org/html/2508.00751v1

## 2. LLM-judge labels / weak supervision

**Headline: a judgment is only reusable relative to (prompt version, model version, doc text version, candidate pool). Log all four with every label.**

1. **Judgment record**: (query_id, doc/segment_id, grade, rationale) + judge model id and snapshot + decoding params + prompt template hash and prompt language + doc text hash / corpus snapshot id + date. Why: prompt wording measurably shifts labels, and swapping the judge model changes agreement with humans — labels without this metadata cannot be trusted across your nightly rebuilds. Sources: Thomas et al., LLMs can Accurately Predict Searcher Preferences (SIGIR 2024, the Bing production account), https://arxiv.org/abs/2309.10621; prompt sensitivity study, https://arxiv.org/pdf/2504.12408; Does UMBRELA Work on Other LLMs? (SIGIR 2025), https://dl.acm.org/doi/pdf/10.1145/3726302.3730317
2. **Adopt the UMBRELA scale as the default grade**: 0 irrelevant / 1 related / 2 highly relevant (answer present but unclear/buried) / 3 perfectly relevant. It is the open reproduction of Bing's assessor (GPT-4o, temperature 0, DNA prompt) and produced the official TREC 2024 RAG qrels, so compatibility is free. Sources: https://arxiv.org/abs/2406.06519 (UMBRELA); https://trec-rag.github.io/annoucements/umbrela-qrels/; large-scale validation that UMBRELA qrels rank systems consistently with human assessment: https://cs.uwaterloo.ca/~jimmylin/publications/3731120.3744605.pdf
3. **Listwise judgments (your reranker orderings) need the exact candidate list + presentation order + window/stride**. LLM rankers/judges have position bias — swapping order can flip outcomes — and permutation distillation (RankGPT → RankZephyr) trains precisely on (candidate list as presented, teacher permutation); RankZephyr's robustness comes from shuffled input orderings and variable windows. Your logged reranker orderings ARE distillation training data iff candidates + order + model/prompt version are kept. Sources: LLMs are not Fair Evaluators, https://arxiv.org/abs/2305.17926; RankZephyr, https://arxiv.org/abs/2312.02724
4. **Pool provenance**: record which retriever(s)/run and pool depth produced the judged candidates. Reused qrels have "holes" that systematically penalize novel systems; track hole rate whenever an unjudged system is evaluated and top up judgments. Sources: Shallow Pooling for Sparse Labels, https://arxiv.org/abs/2109.00062; MS MARCO sensitivity analysis (hole rate), https://arxiv.org/pdf/2112.03396
5. **Human anchor + replicates**: keep a small stratified human-judged subset to calibrate the LLM judge over time (the Bing workflow validates LLM labels against real searcher preferences), and store order-swapped or multi-sample replicates individually, not just the aggregate. Sources: https://arxiv.org/abs/2309.10621; https://arxiv.org/abs/2305.17926

Schema convention: TREC qrels (`query_id 0 doc_id grade`) as the exchange format, with a sidecar JSONL keyed (query_id, doc_id, judge_id, prompt_version, model_version) carrying the metadata; BEIR directory layout (corpus.jsonl / queries.jsonl / qrels.tsv) so pytrec_eval / ranx / ir_datasets tooling works out of the box (https://arxiv.org/pdf/2104.08663).

## 3. RAG / agent telemetry

**Headline: log ids + version stamps, not just text; and record which retrieved chunk the answer actually cited — the cited/not-cited distinction is the highest-value derived label (it is your fetch-after-search signal at the generation layer).**

1. **Adopt OTel GenAI span vocabulary, pinned to a semconv version**: `gen_ai.operation.name` covers `invoke_agent`, `execute_tool`, `retrieval` (plus create_agent, memory ops); attributes `gen_ai.request.model`, `gen_ai.usage.input_tokens` / `output_tokens`, `gen_ai.response.finish_reasons`; input/output captured as events. Caveat: every gen_ai.* attribute is still "Development" stability as of mid-2026 — expect renames. Directly relevant to you: the GenAI semconv repo now includes MCP-specific conventions. Sources: https://opentelemetry.io/blog/2026/genai-observability/; https://github.com/open-telemetry/semantic-conventions-genai; stability status: https://dev.to/azena-ai/opentelemetrys-genai-semantic-conventions-are-not-stable-yet-heres-what-actually-shipped-in-2026-3mke
2. **Retrieval span**: raw query + parsed query, retrieved ids + scores + ranks, retriever/index/embedding version. LangSmith models this as a first-class `retriever` run type (query in, documents out) alongside llm/tool/chain, with feedback records (key, score, comment) attachable by run/trace id and trace→dataset export. Source: https://docs.langchain.com/langsmith/export-traces
3. **Braintrust's span field set is a good minimal schema**: `input`, `output`, `expected`, `scores` (string → 0..1), `metadata`, `metrics` — with `expected` reserved for human corrections, which is what turns production traces into eval datasets. Source: https://www.braintrust.dev/docs/guides/logs/write
4. **Eval-ready quadruple**: RAGAS-style offline eval needs exactly (user_input, retrieved_contexts, response, reference?) per trace for faithfulness / answer relevance / context precision / context recall. If you store retrieved ids only, you must be able to resolve the exact chunk text later — so stamp each trace with corpus snapshot id + doc/chunk hash (your nightly rebuild otherwise silently invalidates old traces). Source: https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/
5. **Answer attribution schema**: TREC RAG's format — a `references` array of retrieved segment ids + answer as an array of sentence objects, each with `citations` as indices into references; support graded per sentence (Full / Partial / No Support). Adopting it makes groundedness offline-scorable and interoperable with the nugget-based autograders. Sources: https://trec-rag.github.io/annoucements/2024-track-guidelines/; TREC 2025 RAG overview, https://trec.nist.gov/pubs/trec34/papers/Overview_rag.pdf
6. **Cost/perf per span**: token usage + latency + model/prompt versions (gen_ai.usage.*) — the fields that let you attribute p50 regressions (e.g. your Haiku query-parse) to a stage.

## 4. Legal-domain labeled datasets and their conventions

Datasets (one line each):
- **COLIEE** (annual; Federal Court of Canada + Japanese statute law): Task 1 case retrieval with binary "noticed case" labels per query case over a candidate pool; embedded citations masked with `FRAGMENT_SUPPRESSED` to prevent label leakage; Task 3 statute retrieval. Source: COLIEE 2025 overview, https://dl.acm.org/doi/10.1145/3769126.3785016
- **LePaRD** (US federal; 21.9M citation instances): fields `dest_id`/`source_id`, courts, dates, cites, `passage_id`, `quote`, `destination_context`; task = context preceding a citation → retrieve the quoted precedent passage; fixed candidate pools of 10K/20K/50K passages. License CC-BY-NC-SA-4.0 — incompatible with your CC0 corpus; build the Swiss equivalent from your own citation graph rather than mirroring. Sources: https://aclanthology.org/2024.acl-long.532/; https://huggingface.co/datasets/rmahari/LePaRD
- **CLERC** (US federal): case retrieval + retrieval-augmented analysis generation, built from citations. Source: https://arxiv.org/pdf/2406.17186
- **CaseHOLD** (53K+): citing context as prompt + 5 candidate holdings (1 correct), multiple-choice format. Sources: https://arxiv.org/abs/2104.08671; https://github.com/reglab/casehold
- **LeCaRDv2** (Chinese; 800 queries / 55K candidates): graded relevance 0–3 decomposed into three legal aspects — characterization, penalty, procedure. Sources: https://arxiv.org/abs/2310.17609; https://github.com/THUIR/LeCaRDv2
- **GerDaLIR** (German; 123K queries): precedent retrieval from Open Legal Data, citation-derived labels. Source: https://aclanthology.org/2021.nllp-1.13/
- **BSARD** (Belgian French; 1.1K citizen questions → 22.6K statutory articles, jurist-labeled). Source: https://zenodo.org/records/5217310
- **Swiss (rcds / Niklaus group, all on HF)**: `swiss_doc2doc_ir` — 141K FSCS decisions, queries = facts/considerations sections, targets = `cited_rulings` (decision ids) + `laws` (UUIDs), temporal splits 2002-15 / 2016-17 / 2018-22, CC-BY-4.0 — the closest existing schema to anything you would build (https://huggingface.co/datasets/rcds/swiss_doc2doc_ir); `swiss_citation_extraction` — token-level CITATION/LAW NER over 131K FSCS cases (https://huggingface.co/datasets/rcds/swiss_citation_extraction); `swiss_judgment_prediction` — 85K cases, binary outcome, de/fr/it (https://huggingface.co/datasets/rcds/swiss_judgment_prediction); `swiss_criticality_prediction` — citation-derived criticality labels via semi-automated labeling (https://arxiv.org/pdf/2410.13460); SLDS 20K leading-decision summarization (https://arxiv.org/abs/2410.13456)

Conventions to adopt so your datasets are compatible:
1. TREC qrels + BEIR directory layout + ir_datasets registration (tooling for free).
2. Citation masking à la COLIEE (`FRAGMENT_SUPPRESSED`) wherever document text contains the label — your citation graph leaks labels into decision text otherwise.
3. Temporal splits by decision year (swiss_doc2doc_ir's 2002-15/16-17/18-22 pattern) — matches a corpus that grows nightly and prevents leakage.
4. Graded 0–3 relevance with legal-aspect facets (LeCaRDv2) rather than binary.
5. Language field + parallel cross-lingual qrels (feeds your cross-lingual MRR benchmark).
6. Permissive license (CC0/CC-BY): LePaRD's NC license is the cautionary example.

## 5. Demand-driven coverage (failed lookups → acquisition)

**Headline: log the parsed target of every failed lookup as a normalized entity (citation string, court, date, docket) with a dedup counter — not just an error reason. That single field turns your existing empty-result log into an acquisition queue.**

1. **Zero/low-result query mining** is standard, documented practice in site/e-commerce/enterprise search: zero-result reports are read as demand evidence and drive content/assortment decisions; root-cause split "exists but not matched" (search bug) vs "does not exist" (coverage gap). Sources: Tunkelang, Making Sense of Null and Low Results, https://dtunkelang.medium.com/making-sense-of-null-and-low-results-a077f37bf8fc; https://www.earley.com/insights/mining-search-logs-content-strategy
2. **Classify abandonment before prioritizing**: good vs bad abandonment (SIGIR 2009) — an empty result for a citation that does not exist, or a query answered by the result-page metadata alone, is not a failure; only bad-empty feeds the queue. You already log empty-result reasons; add the resolution status. Source: Li, Huffman, Tokuda, Good Abandonment in Mobile and PC Internet Search, https://research.google/pubs/pub35486/
3. **Unresolved citation edges as a ranked acquisition queue**: citations extracted from decisions but not resolved to an in-corpus document, ranked by citing frequency and recency — an internal demand graph requiring no user data at all. Direct analog: Wikipedia's GapFinder ranks missing articles by predicted demand (pageviews); validated in a 12K-editor controlled experiment (recommended articles 3.2x more likely to be created). Source: Wulczyn et al., Growing Wikipedia Across Languages via Recommendation (WWW 2016), https://arxiv.org/abs/1604.03235
4. **Library science precedent — DDA/PDA**: NISO RP-20-2014 codifies purchasing monographs at the point of user need; the older purchase-on-demand model used interlibrary-loan request logs as the acquisition trigger. Same logic for prioritizing court outreach (e.g. your BL Kantonsgericht gap): demand evidence ranks the ask. Source: https://www.niso.org/publications/rp-20-2014-dda
5. **RECAP model**: user activity fills archive gaps — every PACER document a user buys is auto-contributed to the public archive. API analog: every user-requested decision you lack becomes a durable, counted ticket; optionally close the loop by acquiring and (where a requester is identifiable) noting availability. Source: https://free.law/recap/

## Cross-cutting design decisions (the short list)

1. **`result_set_id` echoed in every search response + append-only impression log** — the one schema change that unlocks unbiased LTR training (1), reusable listwise judgments (2), and trace joins (3).
2. **Version-stamp everything**: ranker policy, prompt hash, judge model snapshot, index/embedding version, corpus snapshot, doc text hash. Every label and interaction is only valid relative to these; your nightly rebuild makes this non-optional.
3. **Log raw events, derive labels offline** (SAT analogs, skip-above pairs, propensities, demand queue) — derived definitions will change; raw impressions + fetch joins will not.
4. **Store judged/retrieved candidates, not only winners** — negatives are half of every training pair and the whole of pool-bias accounting.
